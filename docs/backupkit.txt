BACKUPKIT — NOTA DE DISEÑO HISTÓRICA

Estado

Documento histórico y no contractual.

Este archivo conserva la intención arquitectónica original de backupkit, pero no define comandos, campos de policy, formato de reportes ni capacidades vigentes.

Autoridad documental

Los contratos vigentes se encuentran en:

- README.md
- docs/policy.md
- docs/report-format.md
- docs/precheck-contract.md
- docs/backup-contract.md
- docs/verify-artifact-contract.md
- docs/notifications.md

Ante cualquier diferencia, prevalecen esos documentos y la implementación cubierta por tests.

Objetivo original

Construir una herramienta reutilizable para backups y validación operativa, externa al runtime de los proyectos consumidores.

La intención central se mantiene:

- evitar scripts de backup distintos por proyecto;
- separar secretos de decisiones operativas;
- ejecutar por CLI o scheduler externo;
- producir evidencia estructurada;
- verificar que el artefacto sea utilizable;
- evitar dependencia con la aplicación principal;
- permitir adapters por motor sin introducir lógica de dominio en el core.

Arquitectura vigente

backupkit core
  -> carga .env y policy.yml
  -> valida configuración
  -> adquiere lock project/resource
  -> resuelve adapter por resource.type
  -> ejecuta un comando
  -> produce reporte JSON v2
  -> ejecuta housekeeping si corresponde
  -> intenta notificar según policy

Proyecto consumidor
  -> aporta secretos
  -> aporta policy
  -> declara validators SQL cuando aplica
  -> programa la ejecución fuera del runtime web
  -> consume reportes mediante el contrato público

Comandos vigentes

- backupkit precheck
- backupkit backup
- backupkit verify-artifact
- backupkit restore-test

No existe un comando genérico backupkit run.

Capacidades vigentes

- adapter MySQL;
- prechecks de configuración, filesystem, herramientas, conectividad y autenticación;
- dump MySQL real;
- gzip;
- SHA-256;
- metadata sidecar;
- verificación técnica del artefacto;
- restore a base temporal;
- tablas críticas;
- smoke queries;
- validators SQL declarativos;
- cleanup de restore;
- retención por corridas lógicas;
- protección del último backup válido;
- Telegram para WARN y ERROR;
- reportes JSON report_version=2.

Contrato fuerte vigente

Policy:

- artifact.output_dir
- artifact.path
- artifact.metadata_path

No existen aliases de configuración.

Reporte:

- report_version
- metadata
- final_status
- phases[]
- artifacts[]
- validators[]
- notifications[]
- housekeeping
- final_summary

No existen campos legacy duplicados en el nivel superior.

Separación de responsabilidades

backupkit aporta:

- CLI;
- core;
- adapters;
- validación genérica;
- modelo de reporte;
- retención;
- notificaciones.

El consumidor aporta:

- conexión y secretos;
- clasificación del recurso;
- policy;
- validators específicos;
- scheduling;
- almacenamiento y permisos del output.

Límites vigentes

backupkit no debe:

- depender del runtime de un proyecto consumidor;
- ejecutarse desde una request web;
- importar código de dominio;
- adivinar reglas de negocio;
- exponer dumps desde una interfaz pública;
- tratar reportes legacy como contrato alternativo;
- aceptar nombres alternativos de campos.

Ideas históricas todavía no implementadas

Las siguientes ideas pertenecen a roadmap, no al contrato actual:

- adapters Influx o Redis;
- backup schema-only;
- exclusión declarativa de tablas;
- rotación diaria/semanal/mensual avanzada;
- mail o webhooks;
- cifrado;
- upload externo;
- interfaz web propia;
- inferencia automática de criticidad;
- pipeline multi-fase ejecutado por un único comando.

Criterio para promover una idea histórica

Una capacidad pasa a ser vigente únicamente cuando existen:

1. contrato público sin aliases;
2. implementación;
3. tests;
4. documentación canónica actualizada;
5. comandos de validación reproducibles.
